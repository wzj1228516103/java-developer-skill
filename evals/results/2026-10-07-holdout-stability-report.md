# Java Developer Skill：留出诊断与回归稳定性

本阶段使用 `skill-up 0.12.0`、Codex CLI `0.160.0`，请求模型为 `gpt-6.1-sol`。五项任务为事务自调用、支付超时未知结果、百万行导入、动态排序 SQL 和 HTTP 资源关闭。原始留出结果先用于失败归因，再修订 Skill 与 Judge；修订后的同一批题应称为**留出来源的开发回归**，不能宣称未触碰任务上的独立泛化收益。

## 本阶段完整测量结果

`holdout-v6` 在冻结任务、Judge、模型和输入后运行 3 轮，共 5 个任务 × 2 组 × 3 次（30 次执行）。输入清单核验为 46/46；三轮均无 ERROR。由于这些任务曾参与失败归因和修订，本表是**来源任务开发回归稳定性**，不是未触碰任务上的独立泛化证明。

| 平均质量断言通过率 | 100.00% | 88.89% | +11.11pp |
| 整例通过率 | 15/15（100.00%） | 11/15（73.33%） | +26.67pp |
| 最差用例平均质量率 | 100.00% | 77.78% | — |

## 当前主套件与专项回归

修订后的主套件 `eval-v9` 单轮 15 个任务 × 2 组，输入核验 64/64，0 ERROR：with_skill **15/15、平均质量断言 100%**；without_skill 12/15、91.67%，质量差 **8.33pp**。with_skill 平均耗时 93.8 秒、119,915 Token；without_skill 为 55.9 秒、33,392 Token。3 个基线失败均有具体证据：无权限 API 被写成可执行测试、未要求独立连接验证本地提交状态、以及把已有 `PARKED` 恢复设计误判为必须修改。主套件原始结果见 [metrics.json](2026-10-07-main-v9/metrics.json)。

库存定向复跑两组均 1/1；独立事务回归两组均 1/1；三轮事务定向回归 with_skill 3/3，without_skill 2/3。事务回归单独计数，不并入五项留出分母。

## 归因结论

本阶段没有发现需要继续修改的 with_skill 关键能力：事务提交/回滚验证、动态 SQL 边界、远程副作用恢复、资源生命周期和批处理重试在当前 Judge 下均通过。Judge 固定正反例校准为 20/20；库存文本 Judge 的测试计划歧义也已修复。后续若要继续提升，应在新的、未参与调优的真实项目任务上验证，并减少重复入口探测和重复规则读取；不能把本阶段的来源任务结果宣传为独立泛化提升。

## 失败归因与修复

| 发现 | 归因 | 修复与回归 |
|---|---|---|
| 动态排序已提供白名单、输入与分页验证，却因没有固定 Controller/Service 名称被拒绝 | Judge 强制实现层名称 | 接受参数流转、Mapper、适配层等验证入口 |
| 固定安全默认排序被拒绝；业务上下界或明确约定 size=0 空结果也被拒绝 | Judge 把局部策略当成统一契约 | 接受固定安全默认值与有边界的分页契约，继续拒绝原始 SQL 拼接和无界分页 |
| 已用 try-with-resources 且建议观察 close，却因没逐字写“未执行测试”、没用固定 fake/spy 标签被拒绝 | Judge 词面误判 | 接受可观察的 stub/mock/fake/spy；禁止虚构已执行结果，不强制某句声明 |
| 自调用与通知边界正确，却因没逐项枚举 transaction manager 被拒绝 | Judge 要求超过代码审查题 | 接受等价事务配置说明，评分聚焦真实事务与异常语义 |
| 带 Skill 的事务答案只建议“第二步失败后第一步回滚”，缺异常类型与适用规则；随后又缺成功提交对照 | **真实 Skill 验证指导缺口** | 根 SKILL.md 与 TX-001 加入提交/回滚对照、未捕获运行时异常或实际 rollbackFor 前提、独立读取最终状态；新增检查型异常及测试外层事务回归 |
| 批处理采用逐行短事务、有限重试和可查终态，被要求固定写出并发、人工流程与“块回滚” | Judge 排斥等价事务/恢复方案 | 接受逐行原子性测试与可追踪终态；只评必要业务能力 |
| 明确“只读时可重试，有副作用需协议”的条件设计被当成无条件事实 | Judge 混淆假设与现有契约 | 接受条件设计，继续拒绝宣称未知接口已有幂等能力 |
| 已有租约恢复，却被要求同时写数字并发上限与取消机制 | Judge 将“或”解释为“且” | 明确资源上限、停止/取消、租约恢复三者至少一项；保存原答案及真正危险的基线反例 |
| 库存文本设计题提供测试方案，却被要求实际执行数据库/MQ 测试 | 主套件旧 Judge 歧义 | 明确测试设计与预期状态即可；基线参数冲突、SENDING 租约恢复缺口继续判失败 |
| 相对输出路径导致 final_message 材料越界 | 基础设施 | 包装脚本统一把输出目录转换为绝对路径；不计入质量失败 |

影响最大的真实问题是**事务验证证据不足**：注解、自调用判断和 Mock 调用次数都不能证明生产方法提交或回滚；异常类型、回滚配置和测试外层事务也会改变结论。本次修订只针对这一已复现缺口，没有把每个留出题都加入通用总纲。

## 证据边界

- 主套件历史 `eval-v7`/iteration-32 保留 30 PASS、两组 100%、0pp；不回写历史指标。
- 原始 `holdout-v1` 三轮共 18 PASS、12 FAIL、0 ERROR；`holdout-v2` 共 22 PASS、8 FAIL、0 ERROR。两版均存在已确认 Judge 问题，只用于诊断，不用其差值宣称提升。
- `holdout-v3`、`holdout-v4`、`holdout-v5` 和主套件 `eval-v8` 因评分歧义主动中止，保留原始输出，不计入最终完整采样，也不拼接最好样本。
- 独立事务回归使用 `evals/transaction-regression.yaml`，与五项任务分别报告；固定答案的 Judge 校准亦不计入 Skill 任务通过率。
- 主套件 15 项与五项来源回归分别计算，不能把二者合并成规约覆盖率。文本设计和 Review 不证明完整 Spring 项目、真实数据库事务、真实 MQ 或所有 Java 规约都已验证。
- 宿主登录、全局 Skill 与插件配置沿用本机。即使没有发现基线读取目标 Skill，也不能称为完全空白环境或证明所有注入渠道隔离。网关实际后端模型映射未确认。
- 耗时与 Token 为被测 Agent 原始记录，不含语义 Judge；本轮主套件与来源回归部分重叠运行，历史耗时不可作严格成本因果对照。Token 不能直接换算费用。
