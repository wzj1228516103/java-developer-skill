# 工程结构与架构

规则编号用于架构设计、重构和跨模块 Review；架构名称不是强制目标，业务复杂度和已有边界优先。

## ARCH-001 依赖方向与跨层调用

级别：MUST
适用：Controller、应用服务、领域层、Repository 和基础设施模块。

规则：依赖方向从接口/应用层指向领域和基础设施的抽象；避免 Controller 直接访问 Mapper、跨模块绕层调用。

正例：应用服务依赖 Repository 接口，由基础设施提供实现。

反例：Controller 直接拼 SQL，或一个模块绕过应用服务调用另一个模块的 Mapper。

例外：简单内部查询可以保持轻量，但不能绕过权限、事务和公共契约边界。

## ARCH-002 对象职责隔离

级别：MUST
适用：API 请求/响应、领域逻辑和持久化模型。

规则：DTO/Command、领域对象、持久化对象、Response 按职责隔离；只有确有理由时才共享类型。

正例：请求 DTO 只承载输入，Entity 只承载持久化映射，Response 只暴露允许字段。

反例：直接把 Entity 作为公共 API 请求和响应对象。

例外：明确受控的内部接口可以复用类型，但要记录兼容和字段暴露风险。

## ARCH-003 公共模块边界

级别：SHOULD
适用：common、utils、shared 和跨业务模块。

规则：公共模块保持小而稳定，避免把业务逻辑塞进 `utils/common`；模块边界通过接口、事件或明确的应用服务沟通。

正例：公共模块只提供无业务状态的基础能力，业务规则留在所属模块。

反例：建立巨型 common 包，把订单、用户和支付逻辑混在一起。

例外：经过多个模块验证且语义稳定的能力可以下沉，但应有维护负责人。

## ARCH-004 架构选择与渐进演进

级别：SHOULD
适用：新模块设计、遗留系统重构和架构评审。

规则：采用 DDD、传统分层或六边形架构时，以业务复杂度、团队能力和迁移成本为依据，不把架构名词当作质量证明。

正例：先为高风险边界建立回归测试，再小步隔离模块和依赖方向。

反例：为了追求架构形式一次性重写存量系统，或无业务收益地增加多层抽象。

例外：组织级标准可以要求统一架构，但仍需说明模块边界和落地成本。
